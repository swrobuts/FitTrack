US-2: Kennzahlen und Erwartungswerte

Hier entscheidet sich, ob die Tests etwas beweisen. Die Erwartungswerte für Gesamtdistanz, Wochenschnitt und Lieblingssportart rechnet die Gruppe selbst aus den acht Testdaten, mit dem Taschenrechner, vor dem ersten Prompt. Wer die Werte vom Modell erzeugen lässt, prüft nur, ob die KI mit sich selbst übereinstimmt. Dazu kommt der Randfall, an dem generierter Code am häufigsten versagt: die leere Liste.

Erwartungswerte von Hand statistik.py ohne FastAPI Kalenderwochen mit Lücke Randfall leere Liste monkeypatch

Die Story

US-2 · Kennzahlen. Als Nutzer möchte ich meine Kennzahlen abrufen, damit ich meinen Fortschritt sehe. Akzeptanz: GET /api/stats liefert gesamt_km, durchschnitt_km_pro_woche, lieblingssportart, anzahl, korrekt berechnet für die Testdaten.

„Korrekt berechnet“ braucht eine Definition, sonst ist es nicht prüfbar. Die vier Kennzahlen sind so festgelegt:

Der typische Streitpunkt

Wer nur Wochen mit Training zählt, kommt auf 87,5 / 2 = 43,75. Die Definition sagt „von der ersten bis zur letzten Trainingswoche“. Genau solche Diskussionen sind der Grund, warum Akzeptanzkriterien präzise sein müssen, und warum ein Mensch die Erwartung festlegt, nicht das Modell.

monkeypatch

Der letzte Test ersetzt lade_workouts nur für diesen einen Test durch eine Funktion, die eine leere Liste liefert. Deshalb muss main.py die Funktion mit from .daten import lade_workouts importieren und beim Aufruf lade_workouts() schreiben, nicht daten.lade_workouts(). Das steht so im Prompt.

Der Prompt

Dieser Prompt ist auch der Vergleichsprompt für Lab 09: derselbe Text an Claude, an Qwen3-Coder und an ein Generalisten-Modell.

Du bist ein erfahrener Python-Entwickler. Wir bauen mit FastAPI eine kleine
Fitness-App namens FitTrack. Es gibt eine Funktion lade_workouts() in
backend/app/daten.py, die eine Liste von Dictionaries liefert:
{"id": 1, "datum": "2026-06-01", "sportart": "Laufen",
 "dauer_min": 30, "distanz_km": 5.0, "kalorien": 350}

Aufgabe: Implementiere GET /api/stats.

1. Neue Datei backend/app/statistik.py mit einer reinen Funktion
   berechne_stats(workouts: list[dict]) -> dict, ohne FastAPI-Import.
   Rückgabe:
   - gesamt_km: Summe aller distanz_km, gerundet auf 1 Nachkommastelle
   - durchschnitt_km_pro_woche: gesamt_km geteilt durch die Anzahl der
     ISO-Kalenderwochen von der Woche des ersten bis zur Woche des letzten
     Trainings, beide inklusive (Wochen ohne Training zählen mit),
     gerundet auf 1 Nachkommastelle
   - lieblingssportart: Sportart mit der größten Summe distanz_km,
     bei Gleichstand die alphabetisch erste
   - anzahl: Anzahl der Einheiten
   Leere Liste: 0.0, 0.0, None, 0
2. Pydantic-Modell Stats in backend/app/models.py (lieblingssportart: str | None)
3. Route in main.py: GET /api/stats mit response_model=Stats, die
   berechne_stats(lade_workouts()) zurückgibt. Import so:
   from .daten import lade_workouts

Prüfpunkte für die Antwort

  • Zählt der Code die leere Woche mit? len(set(wochen)) zählt nur Wochen mit Training und liefert 43,75. Der Test fängt das.
  • Wo wird gerundet? Erst am Ende, nicht bei jeder Teilsumme.
  • Ist der Gleichstand behandelt? Der Test prüft ihn nicht. Was tun, wenn das Modell ihn weglässt? Test ergänzen oder bewusst zurückstellen, aber entscheiden.
  • Enthält statistik.py einen FastAPI-Import? Dann ist die Trennung verfehlt.
  • Montag über isocalendar() oder weekday()? Beides richtig. Am Jahreswechsel zeigt sich, ob der Code das ISO-Jahr nimmt.
def montag_der_woche(datum_text: str) -> date:
    """Gibt den Montag der Kalenderwoche zurück, in der das Datum liegt."""
    tag = date.fromisoformat(datum_text)
    return tag - timedelta(days=tag.weekday())


def anzahl_kalenderwochen(workouts: list[dict]) -> int:
    """Zählt die Kalenderwochen von der ersten bis zur letzten Trainingswoche, beide inklusive."""
    montage = [montag_der_woche(w["datum"]) for w in workouts]
    erste, letzte = min(montage), max(montage)
    return (letzte - erste).days // 7 + 1


def lieblingssportart(workouts: list[dict]) -> str:
    """Sportart mit der größten Gesamtdistanz. Bei Gleichstand die alphabetisch erste."""
    summe_je_sportart = defaultdict(float)
    for w in workouts:
        summe_je_sportart[w["sportart"]] += w["distanz_km"]
    rangliste = sorted(summe_je_sportart.items(), key=lambda paar: (-paar[1], paar[0]))
    return rangliste[0][0]

Die Rechenlogik kennt weder FastAPI noch SQLite. Sie bekommt eine Liste und gibt ein Dictionary zurück. Genau deshalb lässt sie sich mit acht Zeilen Testdaten prüfen.

Warum die Trennung zählt

statistik.py läuft in der Python-Konsole ohne Server, ohne Datenbank, ohne HTTP. Die Tests über den TestClient prüfen die Integration, die Funktionen selbst wären auch einzeln testbar. Das ist die Testpyramide aus Lab 05, hier zum ersten Mal im Code sichtbar.

Gegenprobe in SQL

Die Kennzahlen lassen sich auch direkt in der Datenbank nachrechnen. Das ist eine gute zweite Quelle für die Erwartungswerte, unabhängig vom Python-Code.

Übungen

Vier Übungen: einmal rechnen, einmal SQL, einmal Randfälle zuordnen, einmal zu Rundung und Wochenzählung.

Zusammenfassung

  • Erwartungswerte kommen aus den Testdaten und vom Menschen, nie vom Modell. Sonst prüft der Test nur Konsistenz.
  • Jede Kennzahl hat eine Definition, die den Randfall benennt. Ohne Definition ist „korrekt berechnet“ nicht prüfbar.
  • Die Rechenlogik liegt in einer Datei ohne Framework. Sie nimmt eine Liste und gibt ein Dictionary zurück.
  • monkeypatch tauscht die Ladefunktion für einen Test aus. Deshalb der Import from .daten import lade_workouts.
  • Auf den Echtdaten: 3963 km, 37,7 km pro Woche, Radfahren, 311 Einheiten.
