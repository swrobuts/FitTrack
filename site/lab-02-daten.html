US-1: Datenhaltung und Workouts-API

Die Trainingsdaten liegen nicht in einer losen Datei, sondern in einer SQLite-Datenbank mit Schema: zwei Tabellen, ein Fremdschlüssel, eine Sicht. Das ist der Schritt, an dem aus einer Übung ein professionelles Datenmanagement wird. Die API liest nur die Sicht, und die Tests lesen eine eigene Datenbank. Beides zusammen macht den Datenzugriff austauschbar und prüfbar.

SQLite · sqlite3 Schema · Fremdschlüssel · Sicht daten.py · models.py FITTRACK_DATA Pydantic

Die Story

US-1 · Daten abrufen. Als Nutzer möchte ich alle meine Trainingseinheiten als JSON abrufen, damit die App sie anzeigen kann. Akzeptanz: GET /api/workouts liefert Status 200 und eine Liste; jedes Element enthält id, datum, sportart, dauer_min, distanz_km, kalorien.

Die Story sagt, was herauskommt. Wo die Daten herkommen und wie sie gespeichert sind, entscheidet das Team. Diese Entscheidung ist der eigentliche Inhalt dieses Labs.

Warum eine Datenbank und keine Datei

Eine JSON-Datei mit 311 Einträgen sieht harmlos aus. Sie hat drei Schwächen, die sich bei jeder wachsenden Anwendung bemerkbar machen: Niemand prüft, ob ein Eintrag vollständig ist. Die Sportart steht 311-mal als Text, ein Tippfehler wie „Lauffen“ ist ein neuer Wert. Und jede Abfrage lädt alles in den Speicher und filtert in Python.

Regeln im Schema

NOT NULL, CHECK (dauer_min > 0), UNIQUE auf dem Namen der Sportart. Die Datenbank weist ab, was nicht passt, bevor die App es sieht.

Ein Name, einmal gespeichert

Die Sportart ist eine eigene Tabelle. Jede Einheit verweist per Fremdschlüssel auf ihre Nummer. Umbenennen heißt: eine Zeile ändern, nicht 169.

Abfragen statt Schleifen

Sortieren, filtern, summieren erledigt SQL. Die App bekommt genau die Zeilen, die sie braucht, in der Reihenfolge, die sie braucht.

Warum SQLite

SQLite braucht keinen Server. Die Datenbank ist eine Datei, und das Modul sqlite3 gehört zur Python-Standardbibliothek. Das Schema, die Abfragen und die Denkweise sind dieselben wie bei PostgreSQL oder MySQL. Für eine App, deren Datenbank als Datei im Container liegt, ist das die passende Wahl.

Das Schema lesen

Die Datei backend/app/data/schema.sql ist versioniert. Die Datenbank selbst erzeugt scripts/generate_workouts.py daraus. Wer das Schema ändert, ändert die Datei und baut neu. So bleibt nachvollziehbar, welche Struktur die Datenbank hat und warum.

PRAGMA foreign_keys = ON;

CREATE TABLE sportart (
    id       INTEGER PRIMARY KEY,
    name     TEXT    NOT NULL UNIQUE,          -- Laufen, Radfahren, Schwimmen, Wandern
    einheit  TEXT    NOT NULL DEFAULT 'km'     -- Einheit der Distanz
);

CREATE TABLE workout (
    id           INTEGER PRIMARY KEY,
    datum        TEXT    NOT NULL CHECK (length(datum) = 10),   -- ISO-Format JJJJ-MM-TT
    sportart_id  INTEGER NOT NULL REFERENCES sportart(id),
    dauer_min    INTEGER NOT NULL CHECK (dauer_min > 0),
    distanz_km   REAL    NOT NULL CHECK (distanz_km >= 0),
    kalorien     INTEGER NOT NULL CHECK (kalorien >= 0)
);

CREATE INDEX idx_workout_datum ON workout (datum);

CREATE VIEW v_workout AS
SELECT w.id, w.datum, s.name AS sportart, w.dauer_min, w.distanz_km, w.kalorien
FROM   workout  w
JOIN   sportart s ON s.id = w.sportart_id;

Drei Dateien, drei Aufgaben

US-1 bringt zwei neue Dateien und eine neue Route. Jede Datei hat genau eine Verantwortung. Das ist keine Stilfrage: daten.py lässt sich so gegen eine andere Datenbank tauschen, ohne dass die API es merkt.

daten.py · Zugriff

Öffnet die Datenbank, liest die Sicht, gibt eine Liste von Dictionaries zurück, schließt die Verbindung. Der Pfad kommt aus FITTRACK_DATA, sonst aus dem Standard neben dem Modul.

models.py · Form

Das Pydantic-Modell Workout mit sechs Feldern. FastAPI prüft damit jede Antwort und erzeugt die Dokumentation unter /docs.

main.py · Route

GET /api/workouts mit response_model=list[Workout] ruft lade_workouts() auf und gibt das Ergebnis zurück. Drei Zeilen.

import os
import sqlite3
from pathlib import Path

STANDARD_DATEI = Path(__file__).parent / "data" / "fittrack.db"

# Die Sicht v_workout liefert je Einheit den Namen der Sportart statt der
# Fremdschlüssel-Nummer. Jüngstes Datum zuerst, bei gleichem Datum höhere id zuerst.
ABFRAGE = """
    SELECT id, datum, sportart, dauer_min, distanz_km, kalorien
    FROM   v_workout
    ORDER  BY datum DESC, id DESC
"""


def datenbank_pfad() -> Path:
    """Pfad zur Datenbank: aus der Umgebungsvariable oder der Standardwert."""
    return Path(os.environ.get("FITTRACK_DATA", STANDARD_DATEI))


def lade_workouts(pfad: Path | None = None) -> list[dict]:
    """Liest alle Einheiten als Liste von Dictionaries, jüngste zuerst."""
    verbindung = sqlite3.connect(pfad or datenbank_pfad())
    verbindung.row_factory = sqlite3.Row      # Zeilen verhalten sich wie Dictionaries
    try:
        zeilen = verbindung.execute(ABFRAGE).fetchall()
    finally:
        verbindung.close()
    return [dict(zeile) for zeile in zeilen]

Der Prompt

Du bist ein erfahrener Python-Entwickler. Wir bauen mit FastAPI eine kleine
Fitness-App namens FitTrack. Es gibt bereits backend/app/main.py:

from fastapi import FastAPI
app = FastAPI(title="FitTrack", version="0.1.0")

@app.get("/health")
def health() -> dict:
    return {"status": "ok"}

Die Trainingsdaten liegen in der SQLite-Datenbank backend/app/data/fittrack.db.
Das Schema (backend/app/data/schema.sql) hat zwei Tabellen und eine Sicht:

CREATE TABLE sportart (id INTEGER PRIMARY KEY, name TEXT NOT NULL UNIQUE, einheit TEXT NOT NULL DEFAULT 'km');
CREATE TABLE workout (id INTEGER PRIMARY KEY, datum TEXT NOT NULL, sportart_id INTEGER NOT NULL REFERENCES sportart(id),
                      dauer_min INTEGER NOT NULL, distanz_km REAL NOT NULL, kalorien INTEGER NOT NULL);
CREATE VIEW v_workout AS SELECT w.id, w.datum, s.name AS sportart, w.dauer_min, w.distanz_km, w.kalorien
                        FROM workout w JOIN sportart s ON s.id = w.sportart_id;

Eine Zeile der Sicht v_workout sieht als Dictionary so aus:
{"id": 1, "datum": "2026-06-01", "sportart": "Laufen",
 "dauer_min": 30, "distanz_km": 5.0, "kalorien": 350}
Sportarten: Laufen, Radfahren, Schwimmen, Wandern. datum ist ISO-Format.

Aufgabe: Implementiere GET /api/workouts. Dafür brauche ich drei Dateien:
1. backend/app/daten.py mit einer Funktion lade_workouts(pfad=None) -> list[dict].
   Sie liest mit dem Standardmodul sqlite3 aus der Sicht v_workout und gibt
   eine Liste von Dictionaries zurück (sqlite3.Row als row_factory).
   Der Pfad zur Datenbank kommt aus der Umgebungsvariable FITTRACK_DATA;
   ist sie nicht gesetzt, gilt backend/app/data/fittrack.db relativ zur
   Datei daten.py (nicht relativ zum Arbeitsverzeichnis). Der optionale
   Parameter pfad überschreibt beides.
   Sortierung in der SQL-Abfrage: ORDER BY datum DESC, id DESC.
   Verbindung nach dem Lesen schließen (try/finally).
2. backend/app/models.py mit einem Pydantic-Modell Workout für die sechs Felder.
3. Ergänzung in main.py: GET /api/workouts mit response_model=list[Workout].

Randbedingungen:
- Nur Standardbibliothek (sqlite3, os, pathlib), FastAPI und Pydantic, kein ORM
- Relative Imports innerhalb von app (from .daten import lade_workouts)
- Deutsche Bezeichner und kurze deutsche Kommentare
- Diese Tests müssen bestehen (die Tests setzen FITTRACK_DATA auf eine
  Testdatenbank mit 8 Einheiten, ids 1 bis 8, Daten vom 2026-06-01 bis 2026-06-21):

[die vier Tests von oben einfügen]

Gib die drei Dateien vollständig aus und erkläre in drei Sätzen deine Entscheidungen.

Prüfpunkte für die Antwort

  • Pfad relativ zur Datei? Path(__file__).parent, nicht relativ zum Arbeitsverzeichnis. Sonst läuft die App nur aus einem bestimmten Ordner.
  • Sortiert die SQL-Abfrage? ORDER BY datum DESC, id DESC. Ein Modell sortiert gern in Python nach oder vergisst die zweite Spalte.
  • Liest der Code die Sicht? v_workout ist der vereinbarte Weg. Ein selbst gebauter JOIN funktioniert auch, verdoppelt aber Wissen, das im Schema liegt.
  • Wird die Verbindung geschlossen? Offene Verbindungen sind der klassische SQLite-Fehler, besonders unter Windows.
  • Ungefragt hinzugefügt? pandas, SQLAlchemy, ein ORM. Nichts davon war angefordert; weglassen.

Übungen

Fünf Übungen: dreimal SQL auf der echten Datenbank, einmal Begriffe, einmal Dateien und Verantwortungen.

Zusammenfassung

  • Zwei Tabellen, ein Fremdschlüssel, eine Sicht. Das Schema liegt versioniert in schema.sql, die Datenbank wird daraus erzeugt.
  • Die App liest nur die Sicht v_workout. Die Datenbank prüft Regeln, bevor die App die Daten sieht.
  • daten.py ist die einzige Datei, die SQL kennt. models.py beschreibt die Form, main.py die Route.
  • FITTRACK_DATA entscheidet, welche Datenbank gelesen wird. Die Tests bauen ihre eigene bei jedem Lauf.
  • SQLite braucht keinen Server. Die Denkweise ist dieselbe wie bei jeder anderen relationalen Datenbank.
