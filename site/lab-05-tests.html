Testkonzept und Abnahme

Generierter Code und generierte Tests stammen aus derselben Quelle. Stimmen sie überein, belegt das wenig. Das Testkonzept von FitTrack trennt deshalb drei Dinge: wer die Erwartung festlegt, was die Maschine prüft und was der Mensch am Gerät prüft. Dieses Lab zeigt an den 15 Tests der Referenzlösung, wie Testpyramide, Akzeptanzkriterien und Definition of Done zusammenspielen.

Testpyramide Test-First Akzeptanzkriterium Definition of Done Review-Checkliste

Der Grundsatz

Wir schreiben die Tests, bevor die KI den Code schreibt.

Dann prüfen wir gegen das Sollverhalten aus der Story, nicht gegen das, was die KI zufällig gebaut hat. Die Reihenfolge ist entscheidend: Ein Test, der nach dem Code entsteht, beschreibt nur das Vorhandene.

Erwartung aus der Story

Der Erwartungswert kommt aus dem Akzeptanzkriterium und aus den Testdaten, gerechnet von einem Menschen. Nie aus der Antwort des Modells.

Sonderfälle mitdenken

Leere Liste, eine einzige Einheit, Wochen ohne Training, Jahreswechsel. Hier versagt generierter Code erfahrungsgemäß zuerst.

Grenze der Selbstprüfung

KI-erzeugte Tests für KI-erzeugten Code sind ein Konsistenznachweis, kein Qualitätsnachweis.

Die Testpyramide

Auch ein Projekt dieser Größe trägt die volle Struktur: viele schnelle Prüfungen der Rechenlogik, weniger Prüfungen der API, wenige Prüfungen am Gerät. Nach oben nimmt der Aufwand je Prüfung zu und die Zahl ab.

Wo die Ebenen im Code liegen

Die Tests in test_api.py laufen alle über den TestClient, prüfen aber verschiedene Dinge: test_stats_durchschnitt prüft eine Rechenregel, test_workouts_felder die Struktur der Antwort, test_index_liefert_html die Auslieferung. Die Funktionen in statistik.py ließen sich auch ohne TestClient prüfen, das wäre die reine Unit-Ebene.

Akzeptanzkriterien

Ein Akzeptanzkriterium ist ein Satz, den man in einen Test oder in eine Prüfung am Gerät übersetzen kann. Zwei Beispiele aus dem Backlog, einmal maschinell, einmal menschlich prüfbar.

Maschinell prüfbar

GET /api/stats liefert gesamt_km, durchschnitt_km_pro_woche, lieblingssportart, anzahl, korrekt berechnet für die Testdaten. Daraus werden fünf Tests mit handgerechneten Werten.

Am Gerät prüfbar

Bei 375 px Breite kein horizontales Scrollen; Karten stapeln sich; Touch-Targets mindestens 44 px. Daraus wird eine Checkliste für das Smartphone, mit messbaren Zahlen.

Nicht prüfbar

„Die App soll schön aussehen“ oder „die Kennzahlen sollen stimmen“ sind Wünsche, keine Kriterien. Wer sie so stehen lässt, streitet im Review darüber, was gemeint war. Die Definition im README, was „stimmen“ heißt, ist die Antwort auf genau dieses Problem.

Definition of Done

Gilt für jede Story gleich und wird nicht je Fall verhandelt.

  • Code läuft lokal ohne Fehler
  • Zugehörige Tests vorhanden und bestanden (pytest)
  • Akzeptanzkriterium der Story nachweislich erfüllt, Demo am Handy
  • Code von mindestens einer weiteren Person nach der Review-Checkliste geprüft
  • Commit mit aussagekräftiger Nachricht und Story-Bezug
Ab Lab 07 prüft GitHub Actions den zweiten Punkt bei jedem Push. Der grüne Haken am Commit ist der maschinelle Teil der Definition of Done.

Review-Checkliste für übernommenen Code

Die Rolle Quality arbeitet die Liste ab, bevor etwas committet wird. Die Fragen zielen auf die Stellen, an denen generierter Code typischerweise Fehler hat.

Endabnahme

Am Schluss steht kein Eindruck, sondern eine Durchsicht mit sieben Punkten, die abgehakt wird.

  • Alle User Stories aus dem Backlog: erfüllt oder bewusst zurückgestellt, dokumentiert
  • pytest läuft komplett durch, alle Tests bestehen
  • App läuft im Docker-Container, /health antwortet
  • Darstellung auf dem Smartphone geprüft: keine horizontalen Scrollbalken, Karten stapeln sich
  • Diagramm zeigt echte Daten aus der API, nichts hartkodiert
  • README beschreibt Setup, Testlauf und Docker-Start
  • Git-Historie zeigt sinnvolle Commits mit Bezug zu den Stories

Übungen

Vier Übungen: Tests den Ebenen zuordnen, Kriterien bewerten, Stories und Kriterien verbinden, ein Review durchführen.

Zusammenfassung

  • Tests vor dem Code, Erwartungswerte vom Menschen. Sonst belegt ein bestandener Test nur, dass Code und Test zueinander passen.
  • Drei Ebenen: Rechenlogik, API, Gerät. Viele schnelle Prüfungen unten, wenige aufwendige oben.
  • 15 Tests, jeder mit Story und Erwartung. Testdaten getrennt von Echtdaten, dasselbe Schema.
  • Ein Akzeptanzkriterium ist ein Satz, der sich in einen Test oder eine Messung am Gerät übersetzen lässt.
  • Definition of Done und Review-Checkliste gelten für jede Story gleich. GitHub Actions prüft den Testlauf bei jedem Push.
